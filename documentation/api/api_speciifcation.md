# API Specification

**Project:** OxyGuard
**Version:** 1.2.0
**Author:** Martin Robinson (System Architect)
**Target Framework:** FastAPI
**Base URL:** `/api/v1`
**Status:** Approved

---

## Purpose

Defines the approved REST API endpoints for the OxyGuard platform.

This specification establishes the communication contract between the ESP32 edge devices, React dashboard, FastAPI backend, and PostgreSQL database.

---

## Dependencies

This specification implements the following approved architectural artefacts:

* Telemetry Data Contract v1.2.0
* Relational Database Schema v1.1.0
* RBAC Security Matrix v1.0.0

All API field names shall remain consistent with the approved Telemetry Data Contract.

# Endpoint Contracts

## 1. POST /login

### Purpose

Authenticates a registered user and returns a JWT access token.

### Request Body

```json
{
  "username": "martin_architect",
  "password": "secure_password_hash"
}
```

### Backend Requirements

* Validate submitted credentials.
* Verify the user exists and is active.
* Generate a JWT access token.
* Return the authenticated user's assigned role.

### Success Response

**200 OK**

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer",
  "role": "Administrator"
}
```

### Error Responses

* **401 Unauthorized** – Invalid credentials.
* **403 Forbidden** – User account disabled.

## 2. POST /telemetry

### Purpose

Receives telemetry transmitted by an ESP32 monitoring device.

### Request Body

Payload must conform exactly to **Telemetry Data Contract v1.2.0**.

```json
{
  "device_id": "ESP32-WARD1-ICU",
  "ward_id": "ICU-A",
  "flow_rate": 14.75,
  "operational_status": "normal",
  "timestamp": "2026-06-08T21:45:00Z",
  "cylinder_capacity": 1200,
  "consumed_volume": 960,
  "cylinder_status": "REPLACED",
  "breathing_variance": 0.006,
  "emr_status": "EMPTY"
}
```

The three cylinder replacement fields are optional for normal flow telemetry. If any one is supplied, all three are required. When a cylinder is `REPLACED` below 90% utilization, the backend creates a medium `residual_gas_waste` alert and calculates remaining volume, unused percentage, estimated oxygen waste, estimated financial loss, and potential savings.

`breathing_variance` and `emr_status` are optional detection inputs. For the same device, qualifying readings must remain continuous for strictly more than 10 minutes. A non-qualifying reading resets that rule's timer. An existing unresolved alert of the same type prevents duplicate alerts.

### Backend Requirements

* Validate the payload against the Telemetry Data Contract.
* Store validated telemetry in `telemetry_logs`.
* Evaluate alert rules.
* Create an alert when abnormal conditions are detected.
* Create a Residual Gas Waste alert when `cylinder_status = REPLACED` and `consumed_volume < 0.90 * cylinder_capacity`.
* Create a high-severity Ghost Flow alert when `flow_rate > 0.5`, `breathing_variance < 0.01`, and the condition has continued for more than 10 minutes.
* Create a high-severity Unauthorized Bed Usage alert when `emr_status` is `EMPTY`, `DISCHARGED`, `TRANSFERRED`, or `UNASSIGNED`, `flow_rate >= 2.0`, and the condition has continued for more than 10 minutes.

### Success Response

**201 Created**

```json
{
  "status": "success",
  "message": "Telemetry logged successfully.",
  "alert_created": true,
  "alert": {
    "alert_type": "ghost_flow",
    "severity": "high"
  },
  "alerts": [
    {
      "alert_type": "ghost_flow",
      "severity": "high",
      "recommended_action": "Verify patient occupancy and close oxygen supply."
    }
  ]
}
```

`alert` remains the first generated alert for backward compatibility. `alerts` contains every alert generated by the reading, including simultaneous rule matches.

### Error Responses

* **400 Bad Request** – Invalid payload.
* **422 Unprocessable Entity** – Contract validation failed.

## 3. GET /devices

### Purpose

Returns registered monitoring devices and their current operational state.

### Success Response

**200 OK**

```json
[
  {
    "device_id": "ESP32-WARD1-ICU",
    "device_name": "ICU Bed 4 Monitor",
    "ward_id": "ICU-A",
    "device_status": "active",
    "last_seen": "2026-06-08T23:30:00Z",
    "created_at": "2026-06-01T08:00:00Z"
  }
]
```

---

## 4. GET /telemetry

### Purpose

Returns historical telemetry for reporting and dashboard visualisation.

### Supported Query Parameters

* `device_id`
* `ward_id`
* `limit`

### Success Response

**200 OK**

Returns telemetry records matching the supplied query parameters.

---

## 5. GET /alerts

### Purpose

Returns active and historical alerts generated by the monitoring system.

### Supported Query Parameters

* `is_resolved`
* `severity`

### Success Response

**200 OK**

Returns alert records matching the supplied query parameters.

---

## 6. POST /alerts/{id}/resolve

### Purpose

Allows an authorised user to resolve an active alert.

### Backend Requirements

* Verify user authentication.
* Verify the user possesses the `resolve_alert` permission.
* Update the selected alert as resolved.
* Record the action in the `audit_logs` table.

### Success Response

**200 OK**

```json
{
  "status": "success",
  "message": "Alert resolved successfully."
}
```

### Error Responses

* **403 Forbidden** – User lacks permission.
* **404 Not Found** – Alert does not exist.
